DiscordBot architecture map and refactoring review

This review covers the four projects in DiscordBot.sln and the test project, at commit b63912c. It maps how the layers connect, ranks the largest classes and files, and recommends which to split first.

Prepared by: Claude Code, from five parallel code-exploration passes Date: 4 September 2026 Status: Findings and recommendations — not an implementation plan

The short version

  • The layering is sound. Core has no reference to Bot. Bot touches Infrastructure concrete types in only two files. The work is inside layers, not between them.
  • Size is concentrated in the Bot host. It holds 105,265 of 155,649 production C# lines, plus all 44,910 Razor lines and 28,552 JavaScript lines.
  • Nine production C# files are at or above 1,000 lines. Three are portal API controllers, one is the SignalR hub, one is a slash-command module, one is a page model, one a service, one a tracing helper, one a DTO bundle.
  • The same code is written many times. Paging and no-tracking queries in 50 of 54 repositories, six moderation commands with one flow each, two near-identical assistant message handlers, 41 hand-typed repository registrations, and per-page fetch boilerplate in JavaScript.
  • The web layer is the least tested part. 11 of 69 page models have tests. The four largest page models have none. No JavaScript tests exist.
  • Documentation has drifted. The web UI agent definition names HTMX and Alpine.js. Neither is loaded anywhere; the stack is vanilla JavaScript, SignalR and Tailwind.

02Architecture map

Each layer described by what it holds, how it is organised, and where its shape is under strain.

Core

Core is a contract library, and mostly a clean one. It holds 62 entities, 158 interfaces (54 repository, 72 service), 131 DTO files, 37 options classes and 31 enums. It references only Identity stores and logging abstractions. The entities form a star around Guild and User, grouped into moderation, audio and voice, AI assistant, scheduling, guild configuration, identity, analytics, Rat Watch and feature requests.

Three things strain the shape. Two DTO bundle files are among the largest files in the solution: DTOs/ModerationDtos.cs at 1,125 lines holds 28 types, and DTOs/PerformanceMetricsDtos.cs at 981 lines holds 37. Several interfaces have outgrown one responsibility, led by INotificationRepository with 23 members and IRatWatchService with 20. And the type SsmlBuildRequest is defined twice, in DTOs/ and DTOs/Tts/, with different and incompatible property sets.

Infrastructure

The data layer follows one pattern well. BotDbContext is 243 lines with 60 DbSets, and OnModelCreating delegates to 57 per-entity configuration classes. One exception is the inline ApplicationUser mapping at lines 95 to 116. The two provider-specific contexts are five-line subclasses, but they live inside the design-time factory files, which hides them.

Repositories are numerous and repetitive. 54 repositories total 9,861 lines. 47 inherit the 636-line generic Repository<T>. Even so, AsNoTracking() is applied by hand in 50 files and paging with Skip and Take is rewritten per repository. The largest are NotificationRepository at 507 lines and 20 public members, and RatWatchRepository at 474.

The services here are the LLM stack and two assistants. AssistantService takes 11 constructor dependencies and DmAssistantService takes 10; both own their own memory-cache key prefixes and rate limiting. Registration is one 137-line method with 41 hand-typed AddScoped repository lines and two near-duplicate provider branches.

Bot host: gateway, commands, services

Startup is thin and composition is spread thin. Program.cs is 337 lines and delegates to 28 extension files totalling 2,244 lines. Together they make 214 registrations: 95 scoped, 88 singleton, 3 transient and 28 hosted services. Nothing documents the order the hosted services need, and BotHostedService at 772 lines both connects the gateway and broadcasts status, so later services depend on it implicitly.

Command modules share no base beyond Discord.Net's. There are 31 modules. ModerationActionModule is 1,002 lines for six commands. Only 7 of 31 modules declare an explicit permission precondition attribute. InteractionHandler at 793 lines owns command registration, dispatch and result handling in one class.

Handlers duplicate. AssistantMessageHandler (292 lines) and DmAssistantMessageHandler (209 lines) carry the same method set: extract the question, send the consent message, send the response.

Services in Bot are there for a reason. The 143 service files depend on Discord.Net or ASP.NET types, so their placement is right. Their size is the issue: RatWatchService 1,021 lines, UserManagementService 996, UserDataExportService 762, PageMetadataService 653, ScheduledMessageService 639, PlaybackService 607.

Web UI and API

The API is 31 controllers over a 74-line base. Three portal controllers dominate: PortalTtsController is 1,834 lines with 20 endpoints and 17 constructor dependencies, PerformanceMetricsController is 1,174 lines with 17 endpoints, PortalSoundboardController is 1,173 lines with 18. The SignalR DashboardHub is 1,195 lines with 15 dependencies. Only PreviewController and the migration command touch the DbContext directly.

The Razor site is 161 views and 69 page models with a 56-partial component library. The largest page models aggregate too much: Admin/Settings is 1,000 lines with 10 handlers, Guilds/Details takes 14 dependencies for 2 handlers, Admin/Performance/Index takes 12 for 2. The largest view, Portal/VOX/Index.cshtml, is 2,747 lines with six inline script blocks. A seven-file Blazor/ folder holds a second, undocumented component system.

JavaScript is script-tag globals, not modules. 68 files total 28,398 lines. 47 of them write to window; one voice-selector widget alone exports more than ten window.voiceSelector_* globals. There is no shared API client, so settings.js makes 9 raw fetch calls and portal-tts.js 8, each with its own error handling. Styling is a 4,136-line hand-authored token stylesheet plus six page-scoped stylesheets.

Tests

Coverage is deep where the code is old and thin where it is large. 183 files hold about 3,213 test methods. Repositories, core services, the hub and the interceptors are thoroughly covered; the ten largest test files are all in those areas. The web layer is not: 14 test files for 143 Bot service files, 14 for 31 controllers, 11 of 69 page models, and no JavaScript tests. One shared helper, TestDbContextFactory, serves 183 files, so fixture setup is repeated.

Inside the largest files

PortalTtsController is an orchestrator wearing a controller's attributes. Its longest method, SynthesizeSsml, runs 266 lines from line 666 and mixes APM span enrichment, validation and synthesis. SendTts is 238 lines. The 17 dependencies span voices, presets, history, playback, moderation logging and settings, which is four resources' worth.

DashboardHub serves nine features from one class. Its 26 methods group into connection, guild groups, status, alerts, bulk purge, performance, system health, audio and notifications. GetCurrentPerformanceMetrics at line 611 reads the process and garbage collector directly and builds the metrics DTO by hand.

ModerationActionModule has no 900-line method. The metrics heuristic merged its commands; the real longest is BanAsync at 165 lines from line 478. The duplication is structural: warn, kick, ban and mute each build a DM embed, send it inside a try block, call CreateCaseAsync, then call the shared BuildActionEmbed. The six CreateCaseAsync call sites are at lines 170, 290, 418, 553, 684 and 827.

PerformanceMetricsController is 17 endpoints of 33 to 94 lines each. Every one validates its range, computes the window, calls a collector and shapes the response inline. GetHistoricalMetrics at line 900 is the clearest case for a query service.

BotActivitySource is table-shaped code written as methods. Its 36 static methods come in matching pairs: a plain Start*Activity and a Start*ActivityWithApm that adds a span and two to four labels. Lines 668 to 729 hold five such wrappers of identical shape. A dictionary of operation name to label list would replace most of the file.

RatWatchService is five services in one. Its 23 public methods cover watch lifecycle, voting and finalisation, statistics and leaderboards, schedule-time parsing, and guild settings, over 8 dependencies. NavTabsViewModel, by contrast, is a false positive: one record, one nested record and three enums, with most of its 834 lines being documentation comments.

04Cross-cutting smells

Patterns that recur across many files. Each is cheaper to fix once than in place.

Duplicated flow

Six moderation commands each rebuild the same sequence. Validate target, confirm, act, notify by DM, write audit, reply with embed. The 1,002-line ModerationActionModule is the visible cost; the hidden cost is that a fix to one path must be repeated five times.

Duplicated handler

Guild and DM assistant handlers are the same pipeline twice. AssistantMessageHandler and DmAssistantMessageHandler share method names and shape. Their backing services also each own a private cache prefix and rate limiter.

Wiring by hand

Registration is manual and flat. 41 repository registrations in Infrastructure and 214 registrations across 28 Bot extension files. Each new entity adds a line in three places. Nothing records the order that 28 hosted services need.

Query boilerplate

50 of 54 repositories reapply AsNoTracking and hand-write paging. The generic base exists but does not offer paged or read-only query helpers, so every repository grows its own.

Client boilerplate

No shared JavaScript API client. Each page script hand-rolls fetch, JSON parsing, anti-forgery headers and error display. Widgets export dozens of window globals instead of one namespace.

Stale documentation

The web UI agent definition names HTMX and Alpine.js. A repo-wide search for hx-, x-data and either library's script finds nothing. The stack is vanilla JavaScript, SignalR from a CDN, and Tailwind.

Diverged duplicate type

SsmlBuildRequest exists twice in Core with different properties. One uses required init-only fields; the other uses mutable annotated fields with different names. A caller can bind to the wrong one and compile.

05Recommendations

Ranked by payoff against effort. The first tier is mechanical and safe; the last tier changes structure.

Do these first

Small, mechanical, and each removes a whole class of repetition

01

Extract one moderation action pipeline and make the six commands call it

1–2 days−600 lines, one path to test

ModerationActionModule.cs repeats validate, confirm, act, notify, audit, reply for warn, kick, ban, unban, mute and purge. A ModerationActionRunner taking an action descriptor collapses this to six thin commands.

Existing tests for the module are the safety net; add one test per action against the runner.

02

Merge the guild and DM assistant handlers behind one pipeline

1 dayone handler, one rate limiter

Introduce an assistant message pipeline that takes a context abstraction for guild versus DM. Move the shared cache key prefix and rate limiting out of AssistantService and DmAssistantService into it. Both services drop below eight dependencies.

03

Add paged and read-only query helpers to the generic repository base

half a day50 repositories shrink

Add QueryNoTracking() and a PagedAsync(query, page, size) helper to Repository<T>, then replace the per-repository copies. Start with NotificationRepository, RatWatchRepository and CommandLogRepository.

04

Register repositories by convention and dedupe the provider branches

half a dayno more copy-paste on new entities

Scan the Infrastructure assembly for IFooRepository to FooRepository pairs. Fold the SQLite and PostgreSQL AddDbContext blocks into one local function that takes the provider delegate. Move the two provider contexts out of the design-time factory files.

05

Fix the diverged SsmlBuildRequest and the stale UI agent doc

an hourremoves a latent bug and a false map

Pick the shape the TTS pipeline uses, delete the other, and fix the call sites. Replace the HTMX and Alpine.js paragraph in .claude/agents/web-ui-portal.md with the real stack.

Split the giants

Each is one file that has become several responsibilities

06

Split the three portal controllers by sub-resource

2–3 days4,181 lines become ~10 focused controllers

PortalTtsController (1,834 lines, 17 dependencies) becomes voices, presets, history and playback controllers. Apply the same to PortalSoundboardController and move PerformanceMetricsController's aggregation into a metrics query service. Routes do not change; the integration tests in PortalTtsIntegrationTests stay valid.

07

Break DashboardHub into feature hubs or a thin hub plus notifier services

2 days15 dependencies drop to 3–4 per hub

Group the 26 hub methods by their nine feature areas and give each area its own hub, or keep one hub whose methods delegate to per-feature notifier services. DashboardHubTests at 1,364 lines shows the current surface is already hard to test whole.

08

Split InteractionHandler and BotHostedService by lifecycle stage

1–2 daysexplicit startup order

Move command registration out of InteractionHandler into its own hosted step. Move status broadcasting out of BotHostedService. Then document the hosted service order in one place, since 28 of them currently rely on registration order.

09

Split the DTO bundles and the oversized interfaces

1 daysmaller diffs, clearer ownership

Break ModerationDtos.cs and PerformanceMetricsDtos.cs into per-feature files. Split INotificationRepository, INotificationService and IRatWatchService along their read, write and broadcast seams. Decompose AssistantOptions (344 lines) into bound sub-sections.

10

Move aggregation out of the heavy page models into services

2 dayspage models become testable

Admin/Settings (1,000 lines, 10 handlers) splits into per-section handlers. Guilds/Details (14 dependencies) and Admin/Performance/Index (12) each get one aggregator service. None of the three has tests today; write them against the new services.

The front end

Larger, and worth doing once a JavaScript test runner exists

11

Introduce a shared API client and one namespace per widget

2 days47 files stop writing to window

An api-client.js owning fetch, JSON, anti-forgery and error toasts replaces the per-page copies in settings.js, portal-tts.js and moderation-settings.js. Fold the voiceSelector_* globals into one object. Add a minimal JavaScript test runner at the same time.

12

Externalise the inline scripts from the VOX, TTS and Soundboard portal pages

2–3 days2,747-line view becomes markup

Portal/VOX/Index.cshtml carries six script blocks and no external file. Move them to portal-vox.js and rebuild the page from the component partials. Decide whether the seven-file Blazor/ folder is a migration target or an experiment, and document the answer.

07Out of scope and disclosures

This review did not run the build or the tests. All figures come from line counts, grep and regex heuristics over the working tree at commit b63912c. Line counts, file counts and DbSet counts are exact. Constructor dependency counts, public member counts and method-length figures are approximate and should be confirmed in an editor before being quoted.

Things noticed in passing, not assessed. PostgreSQL has 27 migrations against 105 for SQLite, which may mean the two sets have drifted. SignalR is loaded from a CDN in the layout, which is a supply-chain and offline consideration. Core references Identity stores, which pulls ASP.NET Identity into the domain project. Test files are as large as the code they test, with one shared helper for 183 files.

Not covered. Runtime performance, security, database schema quality, the DocGen project beyond its size, and the content of the 132 migration files.
