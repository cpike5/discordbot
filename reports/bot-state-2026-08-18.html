Everything in this section was measured today, on this container, at commit f0fedc9. Nothing here is inferred from documentation.

03Data and runtime

Two questions decide whether this system is safe to deploy: do the two database providers agree, and does the background work have an owner. Both answers are good.

The providers are in step. The repository keeps two migration sets. SQLite has 50 migrations in Migrations/Sqlite/. PostgreSQL has 13 in Migrations/Postgresql/, because InitialPostgresql squashes the earlier history into one baseline. Both sets end at the same migration, AddFeatureRequests, dated 1 April 2026. Every feature migration since the PostgreSQL baseline exists in both sets.

62 entities back the features. src/DiscordBot.Core/Entities/ holds them. DiscordBot.Core also declares 151 interfaces, which is what lets the test suite mock a system this size.

Provider selection

Database:Provider chooses Sqlite or PostgreSql. Omit it and the app reads the connection string instead. A migrate-data command moves data between the two.

28 hosted services run in the background. They fall into four jobs. Ten collect, aggregate or broadcast metrics. Eight delete expired rows under retention and cleanup policies. Five execute scheduled work — reminders, scheduled messages, Rat Watch, member sync and voice auto-leave. The last five run the Discord client, drain the audit log queue, refresh OAuth tokens, register the APM filters and warm the VOX clip library. A BackgroundServiceHealthRegistry tracks their health, and two health checks report on the database and the Discord gateway.

The web side exposes 31 API controllers, 161 Razor pages and one SignalR hub, DashboardHub. The portal splits into 30 admin pages, 31 guild pages, 10 portal pages and 8 account pages, over 67 shared partials.

Part two · what is moving, and what to watch

04In flight

One piece of work is open. It is parked at a clean boundary, which means picking it up costs nothing beyond reading the plan.

Blazor Phase 0 is done, tested and pushed. Commit bdaeb7c added a Blazor Server islands foundation to src/DiscordBot.Bot/Blazor/: two shared components (UiButton, UiToggle), two interop wrappers for theme and toasts, a debouncer, and a FoundationProbe island on /Components that proves circuit, interop and component parity end to end. The merge landed as PR #1927.

Slice 1 was never started. The handoff document docs/architecture/blazor-modernization-handoff.md names Moderation Settings as the next slice. It states that nothing is half-finished. The file tree agrees: seven files, all foundation, no page conversions.

Good news for whoever resumes

The plan, the phasing and the debounce rules are already written in docs/architecture/blazor-modernization-selective-plan.md. The next person reads two documents and starts on Slice 1.

05Risks

Five findings, ranked by what each unlocks per unit of work — not by size. The first three are hours of work. The fourth is a decision. The fifth is a question only the owner can answer.

Fix these first

Small, mechanical, and each one removes a whole class of surprise

01

Upgrade the four OpenTelemetry packages carrying advisories

an hour4 open advisories

The build emits four NU1902 warnings. Three name OpenTelemetry.Exporter.OpenTelemetryProtocol 1.14.0 and one names OpenTelemetry.Api 1.14.0. All four are moderate severity. Both packages ship in the deployed bot, so the advisories apply to production, not just to CI.

Check the advisories for the patched version, raise both package versions, then re-run the suite. Telemetry has 418 tests behind it, so a regression will show.

02

Write tests for Feature Requests and NotX

2–3 dayscovers 10 commands

These two features have zero tests. Feature Requests is 28 source files, and it drives an AI conversation that generates documents. NotX fetches remote pages over HTTP behind 9 slash commands. Both fail in ways manual checks miss: a prompt-injection filter that stops matching, a timeout that never fires, a response size cap that leaks.

Both have options classes with limits already defined — FeatureRequestsOptions and NotXOptions. Test the limits first. That is the cheapest coverage in the repository.

03

Delete the two stray files committed under Pages/

two minutesremoves a trap

Git tracks src/DiscordBot.Bot/Pages/Index.cshtml.cs.bak and Index.cshtml.cs.temp. Both are editor leftovers of the dashboard page model. They compile into nothing, but the next person to grep the dashboard code finds three versions of it.

Delete both and add *.bak and *.temp to .gitignore.

Decide these

Neither is broken today; both get more expensive the longer they sit

04

Resolve the Fluent Assertions licence before any commercial use

a decisionevery test run warns

Every dotnet test run prints a licence notice. Fluent Assertions is free for non-commercial use only, and 182 test files depend on it. If this bot ever runs commercially, the suite needs either a paid subscription or a migration to another assertion library.

A hobby project can ignore this. Record the decision either way, so the notice stops being noise the next reader has to re-evaluate.

05

Test the command modules, or state that you will not

weeks30 modules

1 of 31 command modules has tests — ConsentModuleTests. This has been true since docs/TEST_COVERAGE_GAPS.md recorded it on 1 April 2026. The blocker is real and named in that document: Discord's sealed SocketInteractionContext cannot be mocked without a wrapper.

The choice is to build the wrapper once and unlock 30 modules, or to write down that command modules stay untested by design. The document already lists the minimum cases per module, so the expensive thinking is done.

Not a risk

The provider split. SQLite and PostgreSQL both end at AddFeatureRequests. This is the failure mode a dual-provider repository usually has, and this one does not have it.

Watch

Documentation age. CLAUDE-REFERENCE.md was last updated on 6 April 2026 and does not mention the Blazor foundation. The gap is four months and grows while the repository is idle.

Found in passing

Discord.Net is pinned to a private fork, version 3.19.0-fork, served from six .nupkg files in local-packages/. The build works because those files are committed. Nobody can restore this solution without them, and no note records what the fork changes. That is fine while the files stay in the repository. It becomes a problem the day someone upgrades.
